# Existing visitor analytics repair

Commit 655b767 (16 September 2026) removed TrackVisits from the web middleware. Production has 200 legacy session records ending on 16 September; there are no observations to reconstruct after that date. Legacy visits are untouched, including their original timestamps and data. Their counts are not proven daily uniques: the previous session flag persisted across days and included no bot/Admin filtering. Consequently the existing cards/chart now use only daily_visits; the Total card explicitly reports the excluded legacy session count. Historical zeros before the new collection began mean no new-metric observations, not proof of no traffic. Old data remains in visits for historical inspection; no conversion/backfill was attempted.

daily_visits stores one normalized keyed IP hash per Europe/Bucharest date, enforced by a composite unique constraint. An atomic insert-ignore handles simultaneous requests; the day/hash cache is only an optimization and is populated after insertion, expiring at the next Bucharest midnight (DST aware). APP_KEY is used with domain separation; no raw IP, URL, referrer, user agent or session ID is collected by the new implementation. Rotating APP_KEY changes hashes and can recount an address on the rotation day. Do not rotate it for analytics.

Existing trusted proxy rules are unchanged: request->ip() is authoritative; arbitrary forwarded headers are never read. Known bots/automated clients and empty user agents are excluded, as are all non-allowlisted routes, non-GET, AJAX, non-HTML and unsuccessful responses. User-agent filtering is heuristic: disguised bots may count, and shared NAT addresses count once. Tracking requires a request to reach Laravel; responses served entirely from a proxy cache are not observable.

Today/yesterday are Bucharest calendar dates. Seven/thirty day windows include today and the previous 6/29 dates. Total is the sum of daily unique IPs, not unique people. Nothing resets or deletes rows at midnight. The original Filament cards and line chart retain their layout.

Deployment: additive new-table migration only; inspect production schema first, apply only 2026_10_08_000001_create_daily_visits_table.php before enabling middleware. No old data update/delete. On code rollback keep the new table and collected rows; do not run migration rollback. Config, Stripe and F3 are unchanged. Analytics failures are reported while public responses remain available.
